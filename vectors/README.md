# Hyphaweave conformance vectors (`weave-record/1`)

These are the executable part of the specification: every case is a
`weave-record/1` record or container plus the **hand-authored** conclusion a
conforming verifier must reach. They exist so that independent implementations
(in particular the future Rust verifier, H1) can agree byte-for-byte without
reading the Python reference implementation.

The authoritative sources are
`../epiweave/docs/design/2026-11-07-common-record-format/DECISIONS.md`
(decision draft v0.1 + correction v0.1.1) and the normative spec under
`spec/`. Where this directory and a decision disagree, the decision wins; tell
the Lead.

**All keys and key material in this directory are synthetic and deliberately
published. Never use them for anything real.** See
[`keys/README.md`](keys/README.md).

## Layout

```
vectors/
  index.json                 generated catalog of every case (id, category, target, input, verdict, errors, notices)
  README.md                  this file
  keys/                      synthetic test keys, keyset declarations, test TSA (see keys/README.md)
  external/                  unmodified official cross-check data + SOURCE.json / PROVENANCE.md
  <category>/<case-id>/      one case: expected.json + input file(s)
  frozen/v0.1/               frozen regression copies (see frozen policy below)
```

Categories and their generators:

| category | cases live in | generated by |
|---|---|---|
| `jcs`, `digest`, `sig`, `ref`, `stage`, `actor`, `labels` | `vectors/<category>/` | `tools/gen_vectors.py` |
| `erasure`, `grant`, `key-lifecycle`, `container`, `integrity-levels` | `vectors/<category>/` | `tools/gen_vectors_extra.py` |

`vectors/index.json` is generated last from all case directories by
`tools/gen_index.py`, so it always reflects what is actually on disk.

## Running the vectors

With the reference verifier installed from `verifiers/python`:

```bash
./.venv/bin/python -m hyphaweave_verify.cli vectors vectors
# or, when installed:
hyphaweave-verify vectors vectors
```

Exit code `0` means every case matched its `expected.json`; `1` means at least
one mismatch (or the verifier returned `invalid`/`unverifiable` where vectors
were expected); `2` means usage/IO error. A single case can be inspected with
`hyphaweave-verify record <case>/record.json --keys vectors/keys/keyset` or
`hyphaweave-verify container <case>/container --keys vectors/keys/keyset`
(plus the case's own `args` tokens, if any).

## Case format (`expected.json`)

Each case directory contains `expected.json`, written as WR-CJ canonical JSON
bytes plus one trailing LF. Fields (CONTRACT §16.2):

| field | required | meaning |
|---|---|---|
| `id` | yes | `<category>/<case-id>`, equal to the directory path |
| `category` | yes | one of the twelve categories |
| `target` | yes | `record` or `container` |
| `input` | yes | path relative to the case directory: usually `record.json`, or a `container/` directory, or `container.zip` |
| `verdict` | yes | `valid`, `invalid`, `unverifiable` or `erased` |
| `errors` | yes | **exact set** of expected error codes (empty for valid cases); for invalid cases each case names the single code of the defect it carries |
| `notices` | optional | expected notice codes; matching is *subset* (a verifier may report additional notices) |
| `args` | optional | verifier CLI arguments. Tokens: `@keyset` -> `vectors/keys/keyset`; `@case` -> the case directory; anything else is a path relative to the case directory (e.g. `keys`, `tsa.crt.pem`, `container.zip`) |
| `expected_digest` | optional | expected `records[i].digest` for record targets (computed here by the independent generator, never by the verifier) |
| `expected_resolution` | optional | expected ref-resolution states by reference index for records with `refs` (a `weave.erased` placeholder's `attestation` reference counts as index 0) |
| `expected_container` | optional | recursive subset match against the report's `container` object |
| `records` | optional | per-record subset expectations matched by `id` |
| `notes` | optional | why the case exists, and which contract rule it exercises |

Runner rules: `verdict` exact; `errors` as a set over the container's
top-level and per-record errors; `notices` subset; `expected_digest`,
`expected_resolution`, `expected_container` and `records` as above. Everything
besides `expected.json` inside a case directory is input material.

Additionally, every record-target positive case carries a real signature by
its `actor.key`, so gate 3(a) (bit-flip anti-verification) cannot leave a
flipped input valid. The two deliberate unsigned exceptions, and the handling of
`weave.erased` placeholders (no `sigs` by format; a mutation that keeps the
placeholder valid must still report `erased`, which the QA gate-3 harness treats
as a documented exception), are documented in
[`GATE-3-EXCEPTIONS.md`](GATE-3-EXCEPTIONS.md).

Generation rules that keep the vectors honest:

* generators live in `tools/` and MUST NOT import the reference verifier;
* digests and signatures in the inputs are produced by the independent
  implementations in `tools/` (`wcj.py`, `keyutil.py`, `recordlib.py`), not by
  the verifier;
* expected verdicts and error codes are typed by hand from the contract;
* a negative case names exactly the error class it tests; a rejection with a
  different code is a test failure, not a pass;
* every positive case must also survive gate 3 (bit-flip anti-verification).

## Test keys and key material

`keys/` contains the deterministic synthetic key inventory, the self-signed
`weave.key.declared` keyset used as `--keys @keyset`, and the local RFC 3161
test TSA. See [`keys/README.md`](keys/README.md) for the derivation, the key
id table, and the "these are public test keys" warning. Regenerate with
`./.venv/bin/python tools/make_keys.py` (`--check` proves byte-identical
output).

## External cross-check data

`external/<source>/` holds unmodified official data used by gate 4
(`tools/check_external.py`), with a `SOURCE.json` (name, URL, commit, sha256,
license, retrieval time), `PROVENANCE.md` (what was extracted, how, and the
mapping to our stricter WR-CJ/Ed25519 profile) and `SHA256SUMS` where useful:

* `external/rfc8785-jcs/` - RFC 8785 JCS test data from `cyberphone/json-canonicalization`;
* `external/rfc8032/` - RFC 8032 §7.1 Ed25519 vectors from the RFC Editor copy;
* `external/wycheproof/` - Ed25519 test vectors from `C2SP/wycheproof`.

Downloaded data is treated as untrusted input. It is never read by the
verifier at runtime; only the gate tooling reads it.

## Regeneration

From the repository root:

```bash
./.venv/bin/python tools/make_keys.py             # deterministic test keys (once)
./.venv/bin/python tools/gen_vectors.py           # jcs, digest, sig, ref, stage, actor, labels
./.venv/bin/python tools/gen_vectors_extra.py     # erasure, grant, key-lifecycle, container, integrity-levels
./.venv/bin/python tools/gen_index.py             # vectors/index.json
```

Determinism/idempotence: `make_keys.py --check`, `gen_vectors.py --check` and
`gen_index.py --check` exit non-zero if the checked-in bytes differ from what
the generators produce. The committed RFC 3161 test timestamp replies are
generated once by the local OpenSSL test TSA; the exact commands live in
`vectors/integrity-levels/README.md` (regenerating them changes bytes but not
conclusions). The RSA test-TSA key is generated on the first `make_keys.py`
run and then reused byte-for-byte.

## Frozen regression set

After all gates pass, a representative set of at least 40 cases (all positives
plus the key negatives) is copied **verbatim** into
`vectors/frozen/v0.1/<category>/<case-id>/`, together with a
`vectors/frozen/v0.1/FROZEN.md` recording the freeze date and source commit.
The frozen conclusions must **never** change: gate 7 runs
`hyphaweave-verify vectors vectors/frozen/v0.1` on every CI run. Later
additions get a new frozen version directory instead of editing v0.1.

## Known coverage gaps

Size-limit rejections (`E_JSON_SIZE`, `E_CONTAINER_SIZE`, and the largest
manifest/blob limits) are not exercised by committed vectors because that would
require multi-megabyte fixtures; they are covered by the verifier's unit tests
and should be added here if a downstream verifier needs data-level coverage.
`expected.json` notes on the individual cases document the exact contract rule
each case is derived from.
