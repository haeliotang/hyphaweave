# Hyphaweave conformance vectors (`weave-record/1`)

These are the executable part of the specification: every case is a
`weave-record/1` record or container plus the **hand-authored** conclusion a
conforming verifier must reach. They exist so that independent implementations
(in particular the future Rust verifier, H1) can agree byte-for-byte without
reading the Python reference implementation.

The authoritative source is the normative specification under `spec/`
(`spec/weave-record-1.md` and the per-kind pages), with the decision draft
`2026-11-07-common-record-format/DECISIONS.md` (v0.1 + correction v0.1.1) and
the revision-1 and revision-2 rulings (Inceptless decisions 2026-11-10 #34
and #42) behind it. Where a
vector and the specification disagree, the specification wins; report the
mismatch to the maintainers instead of silently changing a conclusion.

**All keys and key material in this directory are synthetic and deliberately
published. Never use them for anything real.** See
[`keys/README.md`](keys/README.md).

## Layout

```
vectors/
  index.json                 generated catalog of every case (id, category, target, input, verdict, errors, notices)
  README.md                  this file
  GATE-3-EXCEPTIONS.md       documented exceptions for the mutation/byte-flip gates
  keys/                      synthetic test keys, keyset declarations, edge-points, test TSA
  external/                  unmodified official cross-check data + SOURCE.json / PROVENANCE.md
  <category>/<case-id>/      one case: expected.json + input file(s)
  frozen/v0.1-candidate/     frozen-candidate regression copies (see below)
```

Categories and their generators:

| category | generated by |
|---|---|
| `jcs`, `digest`, `sig`, `ref`, `stage`, `actor`, `labels` | `tools/gen_vectors.py` |
| `erasure`, `grant`, `key-lifecycle`, `container`, `integrity-levels` | `tools/gen_vectors_extra.py` |

`vectors/index.json` is generated from all case directories by
`tools/gen_index.py`, so it always reflects what is actually on disk (the
frozen candidate set is validated separately and is not part of the index).

## Running the vectors

With the reference verifier installed from `verifiers/python`:

```bash
./.venv/bin/python -m hyphaweave_verify.cli vectors vectors
# or, when installed:
hyphaweave-verify vectors vectors
```

Exit code `0` means every case matched its `expected.json`; `1` means at least
one mismatch; `2` means usage/IO error. For the `vectors` target the report
`summary` is `{"case_count", "matched", "mismatched"}`. A single case can be
inspected with `hyphaweave-verify record <case>/record.json --keys
vectors/keys/keyset` or `hyphaweave-verify container <case>/container --keys
vectors/keys/keyset` (plus the case's own `args` tokens, if any).

## Case format (`expected.json`)

Each case directory contains `expected.json`, written as WR-CJ canonical JSON
bytes plus one trailing LF. Fields:

| field | required | meaning |
|---|---|---|
| `id` | yes | `<category>/<case-id>`, equal to the directory path |
| `category` | yes | one of the twelve categories |
| `target` | yes | `record` or `container` |
| `input` | yes | path relative to the case directory: usually `record.json`, or a `container/` directory, or `container.zip` |
| `verdict` | yes | `valid`, `invalid`, `unverifiable` or `erased` |
| `errors` | yes | **exact set** of expected error codes (empty for valid cases); for invalid cases each case names the single code of the defect it carries |
| `notices` | optional | expected notice codes; matching is *subset* (a verifier may report additional notices) |
| `args` | optional | verifier CLI arguments. Tokens: `@keyset` -> `vectors/keys/keyset`; `@case` -> the case directory; anything else is a path relative to the case directory (e.g. `keys`, `tsa.crt.pem`, `container.zip`) |
| `expected_digest` | optional | expected `records[i].digest` for record targets (computed here by the independent generator, never by the verifier) |
| `expected_resolution` | optional | expected ref-resolution states by reference index for records with `refs` |
| `expected_container` | optional | recursive subset match against the report's `container` object |
| `records` | optional | per-record subset expectations matched by `id` (e.g. `kind_known=false` for an unknown kind) |
| `notes` | optional | why the case exists, and which specification section it exercises |

Runner rules: `verdict` exact; `errors` as a set over the container's top-level
and per-record errors; `notices` subset; `expected_digest`,
`expected_resolution`, `expected_container` and `records` as above. Everything
besides `expected.json` inside a case directory is input material.

## Test keys and key material

`keys/` contains the deterministic synthetic key inventory:

* `<name>.seed` / `.pub.bin` / `.pub.pem` / `.json` for the ten named test keys;
* `keyset/*.json` — valid `weave.key.declared` records used as
  `--keys @keyset`: `human-1` is the **self-attested root** (earliest
  `recorded_at`, only its self-signature), every later declaration carries
  `body.owner` plus the owner/previous-key counter-signature
  (`key-new` is owned and co-signed by `key-old`);
* `edge-points/` — the deterministic hostile public-key material for the
  Ed25519 boundary vectors: the eight canonical small-order encodings, the
  `x = 0` sign-bit encoding, a non-canonical `y >= p` encoding, and the
  mixed-order key `A = [a]B + T` with its deterministic crafting seed.

See [`keys/README.md`](keys/README.md) for the derivation, the key-id table,
the owner/cosignature table and the "these are public test keys" warning.
Regenerate with `./.venv/bin/python tools/make_keys.py` (`--check` proves
byte-identical output).

## External cross-check data

`external/<source>/` holds unmodified official data used by the external gate
(`tools/check_external.py`), with a `SOURCE.json` (name, URL, commit, sha256,
license, retrieval time), `PROVENANCE.md` (what was extracted, how, and the
mapping to our stricter WR-CJ/Ed25519 profile) and `SHA256SUMS` where useful:

* `external/rfc8785-jcs/` — RFC 8785 JCS test data from `cyberphone/json-canonicalization`;
* `external/rfc8032/` — RFC 8032 §7.1 Ed25519 vectors from the RFC Editor copy;
* `external/wycheproof/` — Ed25519 test vectors from `C2SP/wycheproof`.

Downloaded data is treated as untrusted input. It is never read by the
verifier at runtime; only the gate tooling reads it.

## Regeneration

From the repository root:

```bash
./.venv/bin/python tools/make_keys.py             # deterministic key material
./.venv/bin/python tools/gen_vectors.py           # jcs, digest, sig, ref, stage, actor, labels
./.venv/bin/python tools/gen_vectors_extra.py     # erasure, grant, key-lifecycle, container, integrity-levels
./.venv/bin/python tools/gen_index.py             # vectors/index.json
```

Determinism/idempotence: `make_keys.py --check`, `gen_vectors.py --check`,
`gen_vectors_extra.py --check` and `gen_index.py --check` exit non-zero if the
checked-in bytes differ from what the generators produce (CI runs all four).
The committed RFC 3161 test replies are generated once by the vectors-extra
TSA procedure; the exact commands live in
`vectors/integrity-levels/README.md`. The RSA test-TSA key is generated on the
first `make_keys.py` run and then reused byte-for-byte.

## Gate 3 exceptions

Gate 3(a) flips one seeded bit in every positive input and requires that the
verifier never returns `valid`/`erased` afterwards. The two deliberately
unsigned positive records, the `weave.erased` placeholder shape, and the
ignored unknown-algorithm signature entries (whose bytes are semantically inert)
are documented in [`GATE-3-EXCEPTIONS.md`](GATE-3-EXCEPTIONS.md); everything
else must be covered by a cryptographic binding.

## Frozen candidate set

`vectors/frozen/v0.1-candidate/` contains a deterministic selection of cases
(all positives plus, for each error code, the lexicographically first case that
expects it) copied verbatim from a gated state of the repository, together with
`FROZEN.md` and a `SHA256SUMS` file covering every file. It is a **candidate**
set: the formal freeze — and the promise that these conclusions never change —
starts only when `weave-record/1` v0.1 is accepted by the J1 and J2 round-trip
tests. Until then the candidate may be regenerated after a ruling. The CI gate
validates the file set and checksums and runs the verifier over the candidate
set; removing a case turns that gate red.

## Known coverage gaps

Size-limit rejections (`E_JSON_SIZE`, `E_CONTAINER_SIZE`, and the largest
manifest/blob limits) are not exercised by committed vectors because that would
require multi-megabyte fixtures; they are covered by the verifier's unit tests.
`expected.json` notes on individual cases document the exact specification rule
each case is derived from.
